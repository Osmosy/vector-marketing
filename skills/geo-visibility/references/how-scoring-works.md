# Разбор ответов: как считается и какие грабли сняты

Все эвристики проверены на живых прогонах (DeepSeek API и локальные модели через
ollama-совместимый эндпоинт, 19.09.2026). Ни одна не «на глаз»: каждая появилась
после конкретного ложного результата.

## Формы бренда (`brand_forms`)

Источники форм: `name`, `aliases`, `sites`.

- Из сайта берётся **хост и сегменты пути**, но не имя платформы: `github.com`
  исключён из форм, иначе любой ответ со ссылкой на GitHub «подтверждал» бренд.
  Полный список платформенных хостов — `GENERIC_HOSTS` в скрипте.
- Формы нормализуются (нижний регистр, `ё` → `е`) и дедуплицируются.
- Минимальная длина — 2 символа: односимвольные формы дают сплошные ложные срабатывания.

## Поиск упоминаний (`find_mentions`)

Поиск идёт **по границе слова**: `(?<![а-яa-z0-9])форма(?![а-яa-z0-9])`.
Без этого «вектор» находится внутри «векторный», а «сеть» — внутри «сетевой», и отчёт
получает упоминания, которых в ответе нет.

Пересекающиеся попадания схлопываются: одна и та же позиция, найденная именем и
алиасом, — это одно упоминание, а не два.

## Позиция в ответе (`mention_position`)

Считает **порядковый номер** упоминания в потоке текста, а не «место в топе»:
для вопроса «первая рекомендация или в конце списка» этого достаточно и не требует
разметки структуры ответа. Считаются элементы списка (`1.`, `- `, `**Заголовок**`).

Ограничение: ответ без списка даёт позицию 1 для любого упоминания. В отчёте это
не ошибка — просто менее информативный ответ, и рядом всегда есть сырой текст.

## Тональность (`sentiment_around`)

Окно 220 символов вокруг упоминания, два коротких списка маркеров. Списки **намеренно
короткие**: широкий словарь тональности даёт ложные оценки, а вывод должен быть
защитимым перед клиентом. Ответ целиком не анализируется: в нём почти всегда есть и
плюсы, и минусы разных брендов, и агрегат по всему тексту теряет смысл.

## Ложные упоминания: `ambiguousEntity`

**Живой случай.** На вопрос «что известно про Vector Marketing от Osmosy» модель
ответила про американскую компанию прямых продаж (ножи Cutco) и добавила, что связи
с Osmosy нет. Формально бренд назван 11 раз — примитивный счёт дал бы «упоминается».
Фактически нас не знают.

Как различаем: если в ответе встретилось только **общее имя**, а ни один различающий
признак (алиас или домен из `sites`) — не встретился, ставится
`ambiguousEntity: true`. Такой ответ помечается как требующий ручной проверки и **не
должен попадать в отчёт как «нас рекомендуют»**.

Правило конфига: **для бренда с распространённым названием `aliases` обязателен.**
Без алиасов механизм различения работать не будет.

## «Данных нет»: `claimsUnknown`

Дословный поиск фраз («связи нет») не работает: формулировка живая —
«публично подтверждённой связи между проектом X и компанией Y нет».

Поэтому ищем **два сигнала в одном предложении**: предмет (`связ`, `подтвержд`,
`данн`, `информац`, `найден`, `известн`, `упоминан`) и отрицание (`нет`, `не `,
`отсутств`, `не удалось`). Предложение разбивается по `.?!\n`.

Проверено на 5 формулировках: «связи … нет» → true; «данных о таком проекте нет» →
true; «есть данные о компании» → false; негатив «слабый, жалобы» → false (это
тональность, а не отсутствие знаний).

## Источники: домены и слаги

Два разных сбора, потому что модели называют источники двумя способами:

- `cited_domains` — ссылки и markdown-ссылки → домен без `www.`;
- `source_slugs` — `owner/repo` без ссылки. **Это не редкость, а норма**: в живом
  прогоне все ответы перечисляли репозитории слагом, а `citedDomains` оставался
  пустым. Без этого шага «откуда идёт цитирование» выглядело как «модель ни на что
  не опирается», хотя опора была названа.

Слаг чистится от хвостовой пунктуации (`Marketing/Cutco.` → `Marketing/Cutco`):
иначе в отчёте появляются источники, которых модель не называла.

Домены считаются **по каждой модели отдельно** — у разных движков разные источники,
и общий счётчик на всех делает колонку бессмысленной.

## Транспорт: ключи, базы, retry

- `normalize_base_url` определяет версию API по хвосту базы: `.../v1` не дублируется,
  `.../v4` не превращается в `/v4/v1`. Проверено на z.ai (`/api/paas/v4`) — слепое
  дописывание `/v1` давало 404.
- `api_key_env: ""` — эндпоинт без ключа (локальные модели).
- Retry ×3 с растущей паузой на 429/5xx/сетевые таймауты; 4xx (кроме 429) не
  повторяются — смысла нет.
- `temperature: 0` и фиксированный system-промпт: замер должен быть воспроизводимым,
  иначе «до/после» несравнимы.

## Диагностика прогона

| Симптом | Что это значит |
|---------|----------------|
| `callsFailed > 0` | сводка неполная: перезапустить с `--only-models` для упавших |
| HTTP 410 «was retired at …» | имя модели устарело: заменить в конфиге |
| HTTP 401/403 «Access denied by security policy» | ключ валиден, но заблокирован: это доступ, а не «бренд не найден» |
| HTTP 429 «Insufficient balance» | баланс провайдера пуст |
| Все ответы пустые, `citedDomains` пуст, `sourceSlugs` непуст | норма для моделей без веб-доступа: они называют источники из обучения |

## Границы методики

- Модели без веб-доступа отвечают из обучающих данных: замер показывает **знание**,
  а не то, что «сейчас в интернете». Для проверки именно живого AI-поиска нужны
  движки с поиском (Yandex AI, Perplexity, ChatGPT с browsing).
- AI-ответы меняются при обновлении модели: один и тот же конфиг через полгода даст
  другую картину. Это свойство измерения, а не ошибка скрипта.
- Один прогон — срез, не тренд. Тренд — серия замеров с одинаковым конфигом.
