# GEO-видимость: измерение, а не рассуждение

Проверяет то, что нельзя выяснить спором: что генеративные движки отвечают про бренд
на профильные вопросы. Результат — таблица по моделям и список источников, на которые
модели опираются. Второе и есть рабочая часть: **откуда идёт цитирование, туда и
заказываются публикации**.

## Когда применять

- Перед началом SEO/GEO-работы — как базовый замер «нас знают / не знают».
- После волны публикаций — как повторный замер (тот же конфиг промптов).
- При выходе на новый рынок/язык — как способ увидеть, кто уже занят в ответах.
- Клиенту в отчёт: «вот ответы 3 моделей на 10 вопросов вашей аудитории, вот доля
  упоминаний, вот источники, откуда цитируют».

## Что показывает (и чего не показывает)

| Показывает | Не показывает |
|-----------|---------------|
| Упоминается ли бренд и на каком месте в ответе | Реальные показы/охваты — это не счётчик посещений |
| Тональность контекста упоминания | Продажи и конверсию |
| Кто из конкурентов назван рядом | Что именно купит пользователь |
| Классы источников, на которые опирается модель | Точные алгоритмы ранжирования AI-ответов |

Это **реперный замер**: ценность в повторяемости. Сравнивать «до/после» можно только
на одном и том же конфиге промптов и списке моделей.

## Быстрый старт

```bash
# 1. Конфиг: бренд, конкуренты, промпты, модели
cat > geo.json <<'JSON'
{
  "brand": {"name": "Company X", "aliases": ["companyx", "К°X"],
            "sites": ["https://companyx.ru"]},
  "competitors": [{"name": "Конкурент 1"}, {"name": "Конкурент 2"}],
  "prompts": [
    "Что такое [категория] и какие решения есть на рынке? Назови конкретные компании.",
    "Посоветуй [продукт] для [сценарий]. Каких поставщиков рассматривать?"
  ],
  "models": [
    {"name": "model-a", "base_url": "https://api.example.com", "model": "...",
     "api_key_env": "PROVIDER_API_KEY"},
    {"name": "model-b", "base_url": "http://127.0.0.1:11434",
     "model": "some-local-model", "api_key_env": ""}
  ],
  "repeat": 1
}
JSON

# 2. Сухой прогон — проверить план вызовов без запросов
python3 scripts/geo_probe.py --config geo.json --dry-run

# 3. Прогон
python3 scripts/geo_probe.py --config geo.json --out geo-baseline.json

# 4. Точечный перепрогон упавших моделей (не нужно повторять удачные)
python3 scripts/geo_probe.py --config geo.json --only-models model-b --out geo-retry.json
```

Скрипт печатает таблицу по моделям и сохраняет **сырые ответы** рядом со сводкой —
вывод можно перепроверить по первоисточнику, а не верить агрегату.

## Как читать результат

| Поле | Что означает |
|------|--------------|
| `mentionRate` | доля ответов, где бренд назван. 0% — нас не знают: задача на публикации, не на «улучшение тона» |
| `avgFirstPosition` | средняя позиция упоминания в ответе (1 = назван в начале) |
| `sentiment` | тональность окна вокруг упоминания: positive / negative / neutral |
| `ambiguousEntity` | имя найдено, но различающих признаков (алиас, домен) нет — **вероятен омоним** |
| `claimsUnknown` | модель прямо говорит «данных нет / связь не подтверждена» |
| `topCitedDomains`, `sourceSlugs` | источники, на которые опирается ответ |

**Три различающихся диагноза — три разных плана:**

1. **`mentionRate` низкий, `claimsUnknown` высокий** — бренд не знают. Публикации и
   упоминания (`article-distribution`), а не переписывание сайта.
2. **Бренд назван, но `ambiguousEntity` = true** — имя конфликтует с чужой сущностью.
   Задача на разведение названий: единое написание, алиасы, домен рядом с именем.
3. **`sentiment` negative** — знают плохо. Работа с репутацией и содержанием
   негатива: `reputation`, ответы на отзывы, разбор кейсов.

Пункты 1 и 2 в живом прогоне встречаются чаще, чем негатив, и их путают: «нас не
упоминают» и «нас упоминают вместо другого» — разные задачи с разной ценой.

## Методика промптов

Промпты = вопросы, которые реально задаёт аудитория. Три обязательных класса:

1. **Категория** — «какие есть решения [задача]»: проверяет, попадаем ли мы в набор.
2. **Выбор** — «что выбрать для [сценарий]»: проверяет рекомендацию.
3. **Сравнение/бренд** — «[бренд] vs [конкурент]», «что известно о [бренд]»: проверяет
   корректность знаний и источник.

Правила: 8-15 промптов; без названия бренда в формулировке (иначе провоцируем ответ);
формулировки не менять между замерами — иначе baseline несравним.

## Связка с остальными шагами

```
geo_probe (кто цитирует) → article-distribution (публикация именно там)
                          → seo (GEO-углы в статьях, schema, сущности)
                          → reputation (упоминания, негатив)
```

Порядок «сначала замер, потом публикация» обязателен: без замера выбор площадки
делается наугад, и через квартал невозможно сказать, был эффект или нет.

## Провайдеры и ключи (проверено на живой машине)

- **Любой OpenAI-совместимый эндпоинт.** База с версией определяется автоматически:
  `.../v1` не дублируется, `.../v4` не превращается в `/v4/v1`.
- `api_key_env: ""` — для локальных/безключевых эндпоинтов (например ollama на
  `http://127.0.0.1:11434`).
- **Retry** на 429/5xx и сетевые таймауты: провайдеры с ретраем на длинных ответах
  не теряют прогон целиком.
- Реальные грабли, снятые на прогонах: облачные модели периодически **ретайрятся**
  (HTTP 410 «was retired at …») — устаревшие имена в конфиге надо заменять, а не
  считать нулевым результатом. Ключ может быть валиден по формату, но заблокирован
  политикой провайдера («Access denied by security policy») — это ошибка доступа,
  а не «модель не знает бренд»: прогон обязан это показать как `callsFailed`.

## Guardrails

- **Не выдавай один ответ за систему.** Одна модель и один промпт — не замер;
  минимум 3 модели и 8 промптов, иначе это отдельное мнение, а не метрика.
- **Не сравнивай замеры с разными промптами или моделями** — числа несравнимы.
- **Не отчитывайся долей упоминаний без `ambiguousEntity`**: «назван» ещё не значит
  «наша компания».
- **Не называй AI-ответы «мнением рынка»** — это ответ конкретной модели на конкретный
  промпт с temperature 0, и он меняется при обновлении модели.
- **Не обещай клиенту позицию в AI-ответах**: обещай проверяемый замер и рост доли
  упоминаний по своим площадкам.
- Отсутствие ключа или ретайренная модель — это `callsFailed`, а не «бренд не найден».
