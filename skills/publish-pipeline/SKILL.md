# Публикация: сначала показать payload, потом отправить

Все остальные скиллы пишут черновики. Этот — отправляет. Поэтому у него единственная жёсткая
граница: **ничего не уходит наружу, пока человек не увидел точный payload и явно не сказал
«да» в этом же разговоре.**

Апрув «в прошлый раз», «концепция одобрена» и «ну ты же понимаешь» разрешением не являются.

## Когда применять

- «опубликуй пост», «отправь в webhook», «выложи по календарю»
- строка календаря в статусе `queued` получила апрув и её надо передать наружу

**Не применять:** написание текста (`content-repurposer`, `content-calendar`),
проверка правил сообщества (`community-post-generator`).

## Два пути отправки

1. **Через свой webhook (по умолчанию).** Payload уходит в n8n, Make или любой сервис, который
   принимает JSON: дальше расписанием и постингом управляет система клиента. Это рекомендуемый
   путь: ключи платформ остаются у клиента, скилл их не видит.
2. **Напрямую в API платформы (опция).** Только если у клиента уже настроены свои ключи и он
   сам этого просит. Ключи берутся из переменных окружения, не из текста и не из файлов проекта.

## Схема payload

```json
{
  "id": "2026-11-03-telegram-case",
  "platform": "telegram",
  "schedule_at": "2026-11-03T10:00:00+03:00",
  "title": "…",
  "body": "…",
  "assets": ["company-brain/cases.md#case-3"],
  "utm": "utm_source=telegram&utm_medium=social&utm_campaign=case-3",
  "source_ref": "company-brain/cases.md#case-3",
  "approved_by": "Osmosy"
}
```

Обязательные поля: `id` (он же ключ идемпотентности), `platform`, `title`, `body`, `source_ref`,
`approved_by`. Без `approved_by` payload не отправляется.

## Шаги

1. **Собрать payload** из одобренной строки календаря и текста черновика.
2. **Показать человеку точный текст и адрес назначения** — полностью, без сокращений: это
   единственный момент, когда ошибку ещё можно поймать бесплатно.
3. **Получить явное «да»** на этот конкретный payload в текущем разговоре. Правка текста
   обнуляет апрув: меняется payload — меняется и подтверждение.
4. **Прогнать dry-run** — печатает запрос, ничего не отправляет:

   ```bash
   python3 scripts/publish_webhook.py --payload-file out/post.json --dry-run
   ```

5. **Отправить** с флагом `--confirmed` (без него скрипт откажется):

   ```bash
   MARKETING_WEBHOOK_URL="https://…" python3 scripts/publish_webhook.py \
     --payload-file out/post.json --confirmed
   ```

6. **Записать результат** в календарь: `status: "published"`, `published_at`, `link`; при ошибке
   `status: "failed"` и текст ошибки — без повторов отправки в том же шаге.
7. **Повторная отправка** — только с новым payload (новый `id`) и новым подтверждением.

## Скрипт

`scripts/publish_webhook.py` — только stdlib, без зависимостей:

- адрес: `--url` или `MARKETING_WEBHOOK_URL`;
- `--dry-run` — печатает метод, адрес и тело, не отправляя;
- без `--confirmed` отказывается отправлять и возвращает код 3;
- коды выхода: 0 — отправлено, 1 — ошибка сети или ответа, 2 — плохой вход (нет JSON, нет адреса),
  3 — отказ запускать (нет подтверждения);
- ключи и токены — только из окружения, в payload их быть не должно.

## Правила

- Payload показывается целиком: заголовок, тело, адрес, время. «Тот же пост, что выше» — не
  показ.
- Один payload — одно подтверждение. Батч подтверждается построчно.
- Секреты не попадают ни в payload, ни в репозиторий: только переменные окружения.
- Отправка идемпотентна по `id`: повтор с тем же `id` — новый пост, а не повторная попытка.
- Всё, что ушло, фиксируется в календаре: без записи считается неотправленным.

## Common Pitfalls

- **Отправить, показав «примерно то же».** Лечение: показывать финальный JSON, а не пересказ.
- **Считать апрув календаря апрувом отправки.** Лечение: два разных подтверждения, второе — на
  payload.
- **Хранить ключи в проекте или в payload.** Лечение: только окружение; скан на секреты перед
  отправкой.
- **Отправлять пакетом без построчного подтверждения.** Лечение: одна строка — один payload.
- **Молча повторять при ошибке.** Лечение: `status: failed`, разбор кода ответа, повтор — новым
  шагом.
- **Не записать результат.** Лечение: без записи в календарь отправка считается невыполненной.

## Verification Checklist

- [ ] Payload содержит `id`, `platform`, `title`, `body`, `source_ref`, `approved_by`
- [ ] Точный JSON и адрес показаны человеку
- [ ] Получено явное «да» в этом разговоре
- [ ] `--dry-run` прогнан; запрос совпадает с показанным
- [ ] Секретов в payload нет
- [ ] Результат записан в календарь (`published` + ссылка или `failed` + ошибка)
